## 2. Стек и ключевые решения

| Решение | Выбор | Почему |
|---|---|---|
| Сборка | **Vite 8 + React 19 + TypeScript** | Привычный стек, быстрый dev. Версия Vite закреплена жёстко — см. ниже. |
| Роутинг и пререндер | **React Router 8, framework mode** (`@react-router/dev`) | `ssr: false` + `prerender` раскладывает роуты в готовые HTML. Официально, поддерживается командой Remix. Чистый SPA брать нельзя: Яндекс рендерит JS медленнее и менее надёжно, чем Google, а сайт живёт с локального поиска. |
| Стилизация | **SCSS + CSS Modules** (`*.module.scss`) | Стили скоупятся автоматически, имена классов не конфликтуют. Пакет `sass` (чистый JS), **не `sass-embedded`** — внутри второго `dart.exe`, см. ограничение ниже. |
| Данные | **Supabase** (Postgres + Storage + Auth) | Товары, отзывы, портфолио, заявки. Даёт готовую авторизацию и хранилище картинок для админки (этап 6). |
| Отдача каталога | Фетч из Supabase **на этапе билда** → пререндер | Клиент получает статику, поисковики — готовый HTML. Supabase дёргается при сборке, а не у посетителя. |
| Формы | Serverless-функция хостинга → **Telegram Bot API** | Токен бота нельзя держать в клиенте, нужен хоть какой-то сервер. |
| Хостинг | Vercel / Netlify / Cloudflare Pages | Статика + одна функция. Уточнить у заказчика — см. §11. |
| Анимации | Framer Motion (точечно) | Только появление секций и hover. Без «вау». |
| Иконки | lucide-react | Тонкие контурные — совпадают с макетом. |

### Почему не Next.js
Обсудили и отказались. Единственное, что он давал сверх Vite + пререндера — sitemap,
метатеги и эндпоинт формы «из коробки». Это пишется руками за пару часов и не стоит
церемоний с RSC и `"use client"` на каждом интерактивном фильтре.
`next/image` тоже не аргумент: картинки товаров мы всё равно жмём в WebP скриптом
импорта (§5).

### Почему не vite-react-ssg
Сначала взяли его, но **README самой библиотеки отправляет к React Router**:
«React Router v7 now has built-in SSG support… we recommend using its official SSG
capabilities». Плюс это версия 0.x с небольшим мейнтейнером. Официальный пререндер
снимает этот риск и даёт `meta` экспортом из роута — `react-helmet-async` не нужен.

> Попутно выяснилось: `react-router-dom` — устаревший пакет-обёртка, он отстаёт
> на мажор (7.x против 8.x). Актуальный называется просто **`react-router`**.

Блокировка шла по **репутации конкретного файла**: устоявшиеся версии проходили,

| Пакет | Статус |

| `rolldown@1.2.7` (в составе `vite@8.2.2`) | **заблокирован** — слишком свежий |
| `esbuild` | заблокирован |
| `sass-embedded` (`dart.exe`) | не проверялся, риск тот же → берём `sass` |
| `sharp` (0.35.3 и 0.35.4) | **заблокирован** — обе версии, откат не помогает |
| `lightningcss` | работает |

**Вместо `sharp` — WASM-кодеки** `@jsquash/png`, `@jsquash/webp` и `@jsquash/avif`: чистый
WebAssembly, под политику не попадает. Уменьшение написано своим боксфильтром
(`scripts/optimize-images.mjs`) — усреднение по площади для даунскейла даёт
качество не хуже, а третий wasm-модуль не нужен. Медленнее нативного кода,
но скрипт запускается вручную и раз в жизнь картинки.

**Отсюда закреплённая версия Vite: `"vite": "8.1.5"`, без каретки.**
Пин держался на блокировке и теперь не обязателен. Тогда обновление до 8.2.x
подтягивало `rolldown@1.2.7`, и сборка переставала запускаться
с ошибкой «Cannot find native binding», которая уводит в ложный след про баг npm.

```bash

```

Тот же принцип подтверждён на соседнем проекте `alex-build`: там `vite@8.1.5`
и чистый `sass`, и сборка проходит.

## 3. Дизайн-система (снята с макета)

### Цвета
```css
--brand-600: #3B5BFE;   /* основной синий: кнопки, ссылки, акценты */
--brand-700: #2F49D8;   /* hover */
--brand-50:  #EEF2FF;   /* подложки блоков, иконки */
--ink-900:   #0F172A;   /* заголовки */
--ink-600:   #475569;   /* основной текст */
--ink-400:   #94A3B8;   /* подписи, мелочь */
--surface:   #FFFFFF;   /* карточки */
--bg:        #F8FAFF;   /* фон страницы, чуть голубоватый */
--border:    #E6EAF5;
```

### Типографика
- Шрифт: **Manrope** или **Inter** (кириллица, переменный). Ставим локально через
  `@fontsource-variable/manrope` — без запроса к Google Fonts, чтобы не терять LCP.
- H1 — 3rem, 700; H2 — 2rem, 700; H3 — 1.25rem, 600; body — 1rem, 400; caption — 0.875rem.
- **`line-height` везде безразмерный.** В rem или px он наследуется как жёсткая
  величина, и потомок с другим кеглем получает чужую межстрочную.

### Единицы измерения

| Что | Единица | Почему |
|---|---|---|
| Размеры шрифта, отступы, gap, ширины | **rem** | Масштабируются вместе с настройкой размера шрифта в браузере — это доступность, а не эстетика |
| `line-height` | безразмерный | Наследуется как пропорция, а не как фиксированная величина |
| Рамки, `outline`, тени | **px** | Волосяная линия должна остаться в 1 физический пиксель, иначе на части экранов исчезнет или удвоится |
| Радиусы | **px** | Скругление не должно расти вместе с кеглем |
| Брейкпоинты | **px** | В rem сетка начнёт ломаться не там, где нарисована |

База: `1rem = 16px`. Конверсия делалась скриптом, значения ≤ 2px оставлены как есть.

### Компоненты (общие правила)
- Радиусы: карточки `16px`, кнопки `10px`, бейджи `999px`.
- Тени: очень мягкие — `0 1px 2px rgba(15,23,42,.04), 0 8px 24px rgba(15,23,42,.04)`.
- Карточка: белая, `1px` бордер `--border`, без тени в покое, лёгкая тень на hover.
- Иконки: контурные, синие, в квадрате `40x40` с фоном `--brand-50`.
- Синий баннер-секция (как «Работаю один») — сплошной `--brand-600`, белый текст, радиус `20px`.
- Контейнер: `max-width: 75rem` (1200px), боковые отступы `1.5rem` (моб. `1rem`).
- Вертикальный ритм секций: токены `--section-gap` (3rem) и `--section-gap-sm` (2rem). Мобильное значение обязано быть меньше десктопного.

### Гарнитуры

Заголовочная — Oswald (`--font-display`), текстовая — Manrope (`--font-sans`).

**h3 остаётся на Manrope — решено 2026-09-09.** Сравнение обоих вариантов
на реальных местах лежит на `/dev/type` первой секцией. Oswald — узкий
дисплейный гротеск: он работает на 40–48px, где виден характер, а на 20px
его узость читается просто как сжатый текст. Мест с h3 больше двадцати,
и почти все — плотные карточки, где разборчивость важнее характера.
Возвращаться к вопросу, только если кегль h3 вырастет.

### Палитра — решено 2026-09-09: оставляем нынешнюю

Десять вариантов собраны на `/dev/palette` (настоящие компоненты, токены
переопределены на обёртке), все проверены на контраст — ни одного ниже
4.5:1. Выбор: ничего не менять.

Разбор нынешней всё равно стоит помнить — два его пункта к выбору палитры
отношения не имеют и остаются открытыми:

- **`--bg-alt` и `--border` неразличимы:** отношение контраста 1.017.
  Рамка на подложке нарисована, но её физически не видно.
- **Служебных цветов нет в токенах.** Красный ошибки задан прямо
  в `LeadForm.module.scss` (#fca5a5), цвета успеха нет вовсе. При второй
  форме красный разъедется.

Для истории, чем нынешняя палитра своеобразна: все двенадцать цветных
токенов лежат в диапазоне 215–231° — шестнадцать градусов круга, то есть
одна краска разной светлоты. Насыщенность `--brand-600` при этом 99%
против 19% у `--ink-600`, отчего кнопка — самое яркое пятно экрана.
Это осознанное состояние, а не недосмотр.

### Организация стилей

```
app/styles/
├─ index.scss          # точка входа: токены + reset. Подключается в root.tsx
├─ _tokens.scss        # :root { --brand-600: ... } — CSS custom properties
├─ _breakpoints.scss   # $breakpoints (SCSS map) + миксин mq()
├─ _mixins.scss        # @forward "breakpoints" + container, card, focus-ring, text-preset
└─ _reset.scss
```
Рядом с компонентами — `Button.module.scss`, `Hero.module.scss` и т.д.

В `vite.config.ts` прописан `css.preprocessorOptions.scss.loadPaths: ["app/styles"]` —
поэтому в модулях пишем короткое `@use "mixins" as *;` вместо `"../../styles/mixins"`.
`additionalData` сознательно **не используем**: он подставился бы и в сам `_mixins.scss`,
дав циклический импорт. А `_mixins.scss` делает `@forward "breakpoints"`, так что
один импорт даёт и миксины, и `mq()`.

**Токены — CSS custom properties, а не SCSS-переменные.** SCSS-переменные исчезают
при компиляции; кастомные свойства живут в рантайме — видны в девтулзах,
переопределяются в медиазапросе или на отдельной секции. Для дизайн-системы это важнее,
чем компайл-тайм подстановка.

**SCSS берём ради того, чего нет в CSS:** миксины (медиазапросы, типографские пресеты),
вложенность, `@use` вместо простыни импортов.

```scss
// _breakpoints.scss
@use "sass:map";

$breakpoints: (
  xxs: 420px,   // крупные телефоны
  xs:  480px,   // телефоны в ландшафте
  sm:  640px,   // фаблеты, мелкие планшеты
  md:  768px,   // планшет — здесь ломается большинство сеток
  lg:  1024px,  // ноутбук
  xl:  1280px   // десктоп: контейнер 1200 + отступы
);

// -0.02px, чтобы max-width не пересекался с min-width на границе,
// если когда-нибудь понадобится парный mq-up
@mixin mq($key) {
  @media (max-width: map.get($breakpoints, $key) - 0.02px) { @content; }
}

// использование
.card {
  padding: 24px;                        // десктоп — база
  @include mq(md) { padding: 16px; }    // 768 и уже
}
```

Миксин работает по `max-width`, то есть **desktop-first**: базовые стили пишем
для широкого экрана, дальше только переопределяем вниз. `@include mq(md)`
читается как «до 768».

> **Порядок медиазапросов внутри правила имеет значение.** При `max-width` вьюпорт
> 640px попадает сразу под `md`, `sm` и `xs` — выигрывает тот, что написан последним.
> Поэтому блоки идут **от большего к меньшему**: `lg` → `md` → `sm` → `xs` → `xxs`.
> Перепутанный порядок даст стиль, который «не применяется» без всякой ошибки.

Цена решения: мобильные устройства сначала разбирают десктопные правила и только
потом переопределяют их. Для сайта, где большая часть трафика придёт с телефонов,
это небольшой, но реальный оверхед — на 44 карточках и семи секциях некритично.

> **Ловушка, о которую легко споткнуться:** `_tokens.scss` содержит `:root { ... }`,
> поэтому подключается **один раз** в `index.scss`. Если написать `@use "tokens"`
> в каждом `.module.scss`, блок `:root` продублируется в бандле столько раз,
> сколько компонентов. Через `@use` подключаем только `_mixins` и `_breakpoints` —
> они компайл-тайм и в бандл сами по себе ничего не добавляют.

### Слаги — свои, не поставщика
У поставщика слаг товара это процентно-кодированная кириллица:
`%d0%ba%d0%be%d0%bd%d0%b4%d0%b8%d1%86%d0%b8%d0%be%d0%bd%d0%b5%d1%80-ultima...`
Нечитаемо, разваливается при копировании, плохо выглядит в выдаче.
Скрипт импорта генерирует **свой транслитерированный слаг** из бренда и модели:
`gree-pular-r410-09` — и кладёт его в поле `slug`, а исходный URL остаётся в `source_url`.
Слаг фиксируется при первом импорте и **больше не меняется**: смена URL опубликованной
страницы = потеря позиций.

### Ещё две идеи — после запуска, не в первый релиз

**Гео-посадочные.** Для локального бизнеса это главный SEO-резерв: «установка
кондиционера Заславль / Фаниполь / Дзержинск / Боровляны». Конкуренция там ниже,
чем по Минску. **Но:** 30 страниц по шаблону с подменой города — это дорвеи,
за них прилетает фильтр. Делать 2-3 штуки с реально разным содержанием
(сроки выезда, доплата за расстояние, примеры работ в этом районе) или не делать вовсе.

**Страница под сезонное обслуживание.** «Чистка кондиционера Минск цена» —
низкоконкурентный запрос с повторяющимся спросом каждую весну. Сейчас это
подраздел `/services/[slug]`; если пойдёт трафик — вынести в отдельную посадочную.

   2 кнопки («Подобрать кондиционер» → `/#quiz`, «Оставить заявку» → `/#lead`),
   рендер сплит-системы справа. Снизу — компактная строка из 3 преимуществ
   (Официальная гарантия до 5 лет / Быстрая установка от 1 дня / Честные цены без переплат).

   > **Почему H1 не слоган.** В макете H1 — «Кондиционеры для вашего комфорта»,
   > а ключевая фраза стоит мелкой строкой сверху. Поменяли местами: H1 — второй
   > по весу сигнал после `<title>`, а сайт живёт с локального поиска.
   > Слоган ничего не теряет от того, что стоит обычным абзацем.
2. **Квиз «Подберу за 4 вопроса»** — главный конверсионный блок, ставим высоко на странице (см. §5).
3. **Готовые решения по площади** — 4–5 карточек с ценой «от».
4. **Услуги** — 4 карточки, превью раздела.
5. **«Работаю один — отвечаю за результат лично»** — синий баннер (из макета страницы услуг)
   + под ним **«Как я работаю»**, 5 шагов со стрелками. Вместе отвечают на «почему он» и
   «как это будет» — по отдельности эти блоки слабее.
6. **Работы и отзывы** — сетка фото «до/после» + 2–3 отзыва, ссылки на полные страницы.
7. **FAQ + форма заявки** — аккордеон на 5–6 вопросов, сразу под ним форма.
   Порядок важен: FAQ снимает последние возражения, форма ловит готового клиента.

**Что убрано и почему:**
- «Почему выбирают меня» (4 карточки) — дублировало полосу преимуществ под hero.
- CTA-баннер «Нужна помощь с выбором?» — его работу делает квиз, он занял это место.
- «Популярные модели» — модели уже показаны в решениях и в результатах квиза.
- Отзывы и портфолио как отдельные секции — слиты в один блок доверия.

### Шапка / подвал
- **Меню — 5 пунктов, не больше:** Каталог · Решения · Услуги · Обо мне · Контакты
  + кнопка «Связаться» (синяя, pill). В макете было 6 с Портфолио и Отзывами —
  они выключены до появления контента, а Каталог важнее обоих.
- Квиз в меню не выносим: он второй секцией на главной, кнопкой в hero и ссылками
  `/#quiz` из решений и статей. Отдельной страницы у него нет — см. §5.1.
- Шапка sticky, при скролле — тень.
- Мобильное меню: полноэкранное, кнопка «Позвонить» внизу.
- **Подвал — полная карта сайта:** сюда уходит то, чему не хватило места в меню
  (Цены, Полезное, Политика), плюс контакты, мессенджеры, ИП/УНП.

> 3. **Доверие.** Витрина-агрегатор противоречит позиционированию
>    «работаю один, отвечаю лично», и растёт риск запроса модели, которую он не возит.

### Структура вместо каталога-витрины

**Ядро — «Готовые решения по площади».** Продаём решение, а не SKU; клиент думает
комнатами, а не киловаттами. 4-5 блоков на главной + отдельная посадочная на каждый:

| Решение | Площадь | Цена |
|---|---|---|
| Спальня | до 20 м² | от 1 400 р. под ключ |
| Гостиная | 25-35 м² | от 1 900 р. |
| Квартира-студия | 40-50 м² | от 2 400 р. |
| Офис | 50-70 м² | от 3 100 р. |

*Цифры условные — уточнить у заказчика (§11).*
В каждом решении — 3 рекомендованные модели: **бюджет / оптимум / премиум** — и кнопка заявки.

**Под этим — курируемый каталог на 30-60 моделей.** Только бренды, которые мастер
реально ставит. Выгружаем через API один раз, дальше правим руками в JSON.

**Широту ассортимента отдаём текстом, а не страницами** — блок на главной и в каталоге:

> «Работаю со всем каталогом поставщика — 4000+ моделей.
> Нужной нет на сайте? Позвоните, привезу.»

### Страница решения `/solutions/[slug]`

Целевой запрос — «какой кондиционер выбрать для комнаты 20 метров». Человек пришёл
с вопросом, а не за покупкой: сначала отвечаем, потом продаём.

| Блок | Содержание |
|---|---|
| Хлебные крошки + H1 | Главная → Решения → «Кондиционер для спальни до 20 м²» |
| Вводный текст | 2-3 абзаца своими словами. Это то, за что страницу ранжируют |
| **Расчёт мощности** | «На 20 м² нужно ~2 кВт» + поправки: солнечная сторона, последний этаж, панорамные окна, много техники. Самый полезный блок — отвечает на реальный вопрос и строит доверие |
| **Особенности случая** | Своё для каждого решения (см. таблицу ниже). Ключевой блок против дублей |
| 3 модели | Бюджет / оптимум / премиум, цена «от», кнопка в карточку |
| **Что входит в цену** | Оборудование + стандартный монтаж: трасса до 3 м, кронштейны, вакуумирование, пуск. И честно — **что оплачивается отдельно**: штробление, длинная трасса, автовышка |
| Форма | «Рассчитать точную стоимость» с предзаполненной площадью |
| FAQ | 3-4 вопроса под этот случай → `FAQPage` schema |
| Перелинковка | Соседние решения («а если комната больше?»), каталог с фильтром площади, `/price` |

**Чем решения отличаются друг от друга** — то, ради чего страницы вообще существуют
отдельно:

| Решение | Про что говорим |
|---|---|
| Спальня до 20 м² | **Шум ночью** — главный критерий. Ночной режим, 20-24 дБ, куда вешать, чтобы не дуло на кровать |
| Гостиная 25-35 м² | Распределение потока, чтобы не дуло на диван. Как вписать блок в интерьер |
| Студия 40-50 м² | Один мощный блок против **мульти-сплита на две зоны**. Соседство с кухней |
| Офис 50-70 м² | Работа весь день — **ресурс компрессора**, кто и за чей счёт обслуживает, документы для юрлица |

> Если под конкретное решение сказать нечего сверх площади — **эту страницу
> не создаём**. Лучше три содержательные, чем пять пустых.

**«Что входит в цену» держим в одном месте** (`config/pricing.ts`), а не копируем
в каждую запись решения: состав стандартного монтажа одинаковый, а менять его
придётся во всех четырёх сразу.

### Отбор моделей — квоты и критерии (решение за нами)

Заказчик отдал выбор на наше усмотрение. Берём по квоте на категорию:

| Категория | ID | Берём |
|---|---|---|
| Сплит-системы (основа каталога) | 33 | **20** |
| Мульти-сплит системы | 14646 | **8** |
| Мобильные кондиционеры | 34 | **8** |
| Полупромышленные сплит-системы | 28512 | **8** |
| **Итого** | | **44** |

**Коммерческие категории не берём** — VRF (141), чиллеры (12), прецизионное (22),
холодильное (18), оконные (5). Это оборудование под бригаду и проект, а не под
одного мастера; на сайте оно только размывает позиционирование.
Если понадобятся — квота 8 на категорию, +32 позиции, правка одной константы в скрипте.

- **Бренды:** ограничиваем 6–8 узнаваемыми (Gree, Haier, TCL, Electrolux, Ballu,
  Royal Clima, Dantex, Mitsubishi). Меньше брендов — выше доверие к подборке.
- **Обязательная сетка:** 5 классов площади (20 / 25 / 35 / 50 / 70 м²) × 3 tier
  (бюджет / оптимум / премиум) = 15 позиций-«скелет». Она гарантирует, что квиз
  не упрётся в пустую выдачу ни на одной комбинации.
- В каждом классе площади — **и инверторная модель, и on/off**: без инвертора
  не закрыть ответ «хочу греться зимой».
- **Приоритет `is_in_stock === true`.** «Под заказ» берём, только если иначе
  дыра в сетке.
- Внутри квоты добираем популярными моделями среднего ценового сегмента.

> **Осторожно с `short_description` поставщика.** Он состоит из двух частей: факты
> («сплит-система, мощность 7 кВт, площадь 70 м²») и **их маркетинговый хвост**
> («Купите с установкой ПОД КЛЮЧ! Рассрочка 0% до года, Лизинг и Кредит, работаем с НДС»).
> Хвост копировать нельзя — это чужие условия продажи, мы рассрочку не даём.
> Скрипт импорта режет всё после перечисления характеристик.

### Цены

**Цена оборудования — как у поставщика,** наценка `1.0`. Заказчик зарабатывает на монтаже.
Коэффициент всё равно выносим в `config/pricing.ts` — если решит добавить процент,
это правка одного числа, а не переобход каталога.

**Цены монтажа в API нет** — проверено, `prices` отдаёт только оборудование,
«с установкой» на сайте поставщика считается их фронтом. Поэтому:

```ts
// config/pricing.ts
export const MARKUP = 1.0;              // наценка на оборудование
export const INSTALL_PRICE = {          // TODO: заглушка, уточнить у заказчика
  upTo25m2: 450,
  upTo50m2: 600,
  over50m2: 800,
};
```
- Пока цифры не подтверждены — на карточке показываем **цену оборудования**
  и отдельной строкой «+ монтаж от N р.». Как только заказчик даст реальный прайс,
  переключаем на слитое «от X р. под ключ» — это флаг в конфиге, не переписывание вёрстки.
- Цены готовых решений (§5, таблица) считаются автоматически: самая дешёвая
  подходящая модель + монтаж, округление вверх до 50 р. Руками их не ведём.

### Скрипт импорта `scripts/import-catalog.ts`
Запускается **вручную и редко**, не в CI. Пишет напрямую в Supabase
(`service_role`-ключ, только локально — в браузер он не попадает никогда).

- [ ] Идёт по квотам из таблицы выше, применяет критерии отбора.
- [ ] Нормализует атрибуты в типизированный объект (парсинг чисел из строк «7кВт», «70м2», «34 — 42дБ»).
- [ ] Режет маркетинговый хвост `short_description` (см. выше).
- [ ] Считает `price` = цена поставщика × `MARKUP`.
- [ ] Скачивает изображения, конвертит в WebP WASM-кодеками (`sharp` заблокирован, см. §2), ресайзит 800/400,
      заливает в **Supabase Storage** (бакет `products`, публичное чтение).
      Хотлинк на чужой домен не используем — имена файлов кириллические и могут отвалиться.
- [ ] **`upsert` по `source_id`, не `insert`.** Обновляет только поля поставщика
      (`price`, `specs`, `in_stock`, `images`) и **не трогает** поля, которые ведутся
      руками или через админку: `description`, `tier`, `featured`, `sort_order`,
      `is_published`. Иначе первый же рефреш цен снесёт всю ручную работу.
- [ ] Режим `--refresh-prices` — обновить только цены и наличие.

#### Картинки товаров: мастер и варианты

Двухступенчатая схема, потому что снимки поставщика нужно править руками —
на каждом стоит водяной знак `SWCOMFORT`.

1. **Мастер** — `public/catalog/<slug>.webp`, один файл на снимок, полный размер,
   качество 90. Пишет `import:catalog`. Это исходник, его правят в редакторе.
2. **Варианты** — `<slug>-400.avif` и т.д., четыре файла на снимок. Собирает
   `npm run catalog:variants` из мастеров. Машинный результат, в правках не нуждается.

**Дедупликация по содержимому.** Производитель снимает одну фотографию на серию:
у 07, 09 и 18 BTU корпус один и тот же. Импорт хеширует скачанные байты, и товары
с совпадающим снимком делят один файл. 50 товаров → **35 картинок**. Это и экономит
трафик посетителю (браузер не качает одно и то же по разным адресам), и сокращает
ручную чистку водяных знаков с 50 файлов до 35.

**Текущее состояние:** на сайте отдаются мастера напрямую, `<picture>` временно
убран из `ProductCard` и `product.tsx`. После чистки знаков — `catalog:variants`
и вернуть `<picture>` со `srcset`. Пока каталог тяжелее нужного: 555 КБ вместо ~250 КБ.

**Грабли:** маска «это вариант» не должна быть `-\d+\.webp` — у мульти-сплитов слаг
заканчивается мощностями внутренних блоков (`...-09-09`), и мастер попадает под неё.
Отличать варианты по списку из products.json, а не по имени.
- [ ] Лог: что изменилось в цене, что пропало из наличия у поставщика.
- [ ] `--dry-run` — показать diff без записи.

### Фильтры в каталоге
Только два: **площадь помещения** и **цена**. Плюс сортировка по цене.
Слайдеров по уровню шума, EER и типу фреона не делаем — на 40 позициях они бессмысленны.
Состояние — в URL (`?area=25`), чтобы ссылки шарились.

### Тексты карточек
Спецификации оставляем как есть (это факты), но **описание в 2-3 предложения пишем своё** —
почему мастер эту модель рекомендует и кому. Это единственное, что отличает наши карточки
от карточек поставщика в глазах поисковика. На 40 позициях реально написать; на 800 — нет.

## 5.1 Квиз «Подберу кондиционер за 4 вопроса»

Главный конверсионный инструмент. Живёт **только секцией на главной** (секция 2),
ссылка на него — якорь `/#quiz`. Кнопка «Подобрать кондиционер» в hero скроллит к нему.

> **Почему без отдельной страницы `/quiz`.** Единственный аргумент за неё был рекламным:
> посадочная с одним действием конвертит лучше, чем якорь на главную. Но реклама пока
> не обсуждалась, а цена дубля реальна — одна секция на двух URL требует canonical
> или закрытия от индексации. Компонент самодостаточен: когда дело дойдёт до контекста,
> поднять `/quiz` — полчаса работы. Пока не нужен (см. §12).

### Вопросы
| № | Вопрос | Варианты | Что определяет |
|---|---|---|---|
| 1 | Какая площадь помещения? | до 20 · 20–35 · 35–50 · 50–70 · больше 70 м² | мощность, решение |
| 2 | Что охлаждаем? | квартира · частный дом · офис · другое | тип блока, нюансы монтажа |
| 3 | Нужно ли греться зимой? | да, вместо обогревателя · нет, только охлаждение · не знаю | инвертор / тепловой насос |
| 4 | Ориентир по бюджету? | эконом · оптимальный · премиум · посоветуйте сами | `tier` модели |

### UX — что делает его «красивым и понятным»
- **Один вопрос на экран**, крупные карточки-варианты с иконкой. Клик по варианту
  **сразу листает дальше** — без кнопки «Далее», так вдвое быстрее.
- Прогресс «Шаг 2 из 4» + тонкая полоса заполнения. Кнопка «Назад» всегда доступна.
- Переход между шагами — fade + сдвиг 200 мс. Высота контейнера анимируется, чтобы
  страница не прыгала. Больше никаких анимаций.
- **Результат показываем сразу, без ввода телефона.** Прятать выдачу за контактами —
  главная ошибка таких квизов: убивает доверие и половину конверсии. Телефон просим
  только на шаге «заказать консультацию».
- Вариант «не знаю / посоветуйте» есть в каждом сложном вопросе — не загоняем в тупик.
- Мобильный: одна колонка, тач-таргеты от 56 px.
- Доступность: `role="radiogroup"`, выбор стрелками и цифрами 1–4, фокус переносится
  на первый вариант нового шага, прогресс озвучивается через `aria-live`.

### Экран результата
- Заголовок по-человечески: «Для комнаты 25 м² с обогревом зимой подойдут эти три».
- Строка **«Почему эти»** — одно предложение с объяснением (инвертор, запас по мощности).
- **3 карточки моделей**: бюджет / оптимум / премиум, с ценой «от X р. под ключ».
- Две кнопки:
  - **«Заказать консультацию»** — первичная, синяя. Открывает форму с уже
    подставленными ответами (клиенту ничего не переписывать).
  - **«Посмотреть весь каталог»** — вторичная. Ведёт в `/catalog` с применённым
    фильтром площади: `/catalog?area=25`.
- Ссылка «Пройти заново» — мелко, под кнопками.

### Логика подбора
```
1. Фильтр: specs.areaM2 >= требуемая площадь (с запасом ~15%)
2. Если «греться зимой» → только isInverter === true
3. Из оставшихся берём по одной модели каждого tier, сортируя по priceFrom
4. Если под комбинацию ничего не нашлось (на 40 позициях это будет) →
   экран «Подберу индивидуально» + форма. Пустую выдачу не показываем никогда.
```

### Технические детали
- Ответы кладём в URL главной: `/?area=20-35&place=flat&heat=yes&budget=mid#quiz`.
  Даёт кнопку «Назад» в браузере, шаринг ссылки и измеримый URL результата.
  **Canonical главной всегда `/`** — иначе каждая комбинация ответов уйдёт в индекс
  отдельной страницей. При заходе по такой ссылке — автоскролл к результату.
- Ответы уходят в заявку (`Lead.quizAnswers`) — мастер видит контекст до звонка.
- Цели аналитики: старт квиза, каждый шаг (где отваливаются), показ результата,
  клик по консультации. Отваливание на конкретном шаге — сигнал переписать вопрос.
- Логика подбора — чистая функция в `lib/quiz.ts`, покрыть юнит-тестами,
  включая случай пустой выдачи.

## 5.2 Хранилище: Supabase

### Поток данных
```
swcomfortair API  ──(scripts/import-catalog.ts, вручную)──>  Supabase
                                                                 │
                          админка (этап 6) ─── правки ──────────>│
                                                                 │
                                              (фетч на этапе билда)
                                                                 ▼
                                                    пререндер → статика → CDN
```
Посетитель в Supabase не ходит: он получает готовый HTML. База нужна на сборке
и в админке. Это сохраняет и скорость, и SEO.

### Таблицы
| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `products` | Каталог, 44 позиции | `source_id` (uniq, id у поставщика), `slug`, `name`, `brand`, `type`, `price`, `images[]`, `in_stock`, `specs` (jsonb), `description`, `tier`, `featured`, `sort_order`, `is_published` |
| `solutions` | Готовые решения по площади | `slug`, `title`, `area_from`, `area_to`, `intro`, `power_hint`, `specifics` (jsonb), `faq` (jsonb), `product_ids[]`, `seo` (jsonb) |
| `reviews` | Отзывы | `author`, `text`, `rating`, `date`, `is_published`, `sort_order` |
| `portfolio` | Работы «до/после» | `title`, `description`, `images[]`, `date`, `is_published` |
| `leads` | Заявки (история сверх телеграма) | `name`, `phone`, `message`, `source`, `product_id`, `quiz_answers` (jsonb), `status`, `created_at` |

**Storage:** бакет `products` (картинки товаров, публичное чтение),
бакет `portfolio` (фото работ, публичное чтение, загрузка из админки).

**Разделение полей `products` — важное:**
- *Поля поставщика* (`price`, `specs`, `in_stock`, `images`) — перезаписываются импортом.
- *Наши поля* (`description`, `tier`, `featured`, `sort_order`, `is_published`) —
  импорт их не трогает, ведутся руками и через админку.

### RLS — включить сразу, на всех таблицах
- `products`, `solutions`, `reviews`, `portfolio`: **anon читает только `is_published = true`**,
  пишет — только `authenticated`.
- `leads`: **anon не может ни читать, ни писать.** Запись — только через
  serverless-функцию с `service_role`. Там персональные данные, читать их из браузера нельзя.

### Ключи
| Ключ | Где живёт | Правило |
|---|---|---|
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` | клиентский бандл | Так и задумано — но **только при включённом RLS**. Без RLS anon-ключ = открытая база. |
| `SUPABASE_SERVICE_ROLE_KEY` | скрипт импорта + `api/lead.ts` | **Никогда** с префиксом `VITE_`. Обходит RLS полностью. |

### Пересборка после правок
Правка в админке не видна на сайте, пока не пересобрали статику. Решение:
Database Webhook в Supabase → build hook хостинга. В админке — кнопка
«Опубликовать изменения» с индикатором, чтобы заказчик понимал, что происходит.
Каталог меняется редко, ребилд раз в правку — нормально.

### Типы
`supabase gen types typescript` → `src/types/database.ts`, генерируем при изменении схемы.
Руками типы таблиц не пишем — разъедутся.

### Если Supabase недоступен на сборке
Билд **падает с ошибкой**, а не выкатывает пустой каталог. Для локальной разработки
держим снапшот `src/data/seed.json` — он же годится, чтобы поднять базу с нуля.

### Правило совместного хранения файлов

Связанные файлы лежат в одной папке, названной по сущности. Имена файлов внутри
сохраняются — никаких `index.tsx`, иначе во вкладках редактора десяток одинаковых
названий.

```
app/routes/services/         app/components/ui/Button/
├─ service.tsx               ├─ Button.tsx
├─ service.module.scss       └─ Button.module.scss
├─ services.tsx
└─ services.module.scss
```

### Куда класть компонент

Решает **число потребителей**, а не то, как компонент выглядит:

| Потребителей | Где живёт | Примеры |
|---|---|---|
| Один роут | Внутри папки этого роута | `routes/home/Hero/`, `routes/home/QuizTeaser/` |
| Несколько роутов | `components/sections/` | `WhyMe`, `Faq` |
| Везде, примитив дизайн-системы | `components/ui/` | `Button`, `Card`, `Section`, `IconBox` |
| Обвязка страницы | `components/layout/` | `Header`, `Footer`, `PageHeader`, `Breadcrumbs` |
| Фича с данными и логикой | `features/<имя>/` | `catalog`, `quiz` — появятся на этапе 3 |

**Поднимаем наверх по факту второго потребителя, а не заранее.** `Hero` и
`SolutionsPreview` лежали в `components/sections/`, хотя используются только
главной — это лишний уровень между компонентом и единственным местом,
где он нужен.

Обратное тоже верно: **компонент, который читает данные напрямую из `data/`,
переиспользовать нельзя.** `Faq` жёстко брал `data/faq.ts`, поэтому на странице
услуги пришлось написать такую же разметку заново. Теперь вопросы приходят пропсом,
и один компонент обслуживает и главную, и услуги, и будущие страницы решений.

Два уточнения, без которых правило вырождается:

1. **Папка нужна только там, где есть что группировать.** Один-единственный файл
   лежит плоско: `routes/catalog.tsx`, `components/sections/Proof.tsx`. Появятся
   стили — появится и папка.
2. **Родственные роуты кладутся файлами в общую папку, а не папка в папку.**
   Список и деталь раздела живут вместе: `services/services.tsx` (список `/services`)
   и `services/service.tsx` (деталь `/services/:slug`). Вложенность
   `services/services/services.tsx` — это про один и тот же раздел трижды.

**Что даёт framework mode из коробки** (и что не надо писать руками):
- Метатеги — экспорт `meta` из роута, попадают в статический HTML. `react-helmet-async` не нужен.
- Данные на сборке — `loader` пререндеренного роута выполняется в момент билда.
- Типы роутов — `react-router typegen` генерирует `./+types/*`, руками не пишем.

**Что всё равно делаем сами:**
- `sitemap.xml` — скрипт `gen-sitemap.ts` в `postbuild`, обходит роуты + слаги из Supabase.
- OG-картинки — статические, по одной на раздел.
- Оптимизация изображений — `npm run images`: WASM-кодеки → AVIF + WebP, четыре ширины,
  <picture> с srcset и preload LCP-картинки из `links` роута.
- Ленивая загрузка — `loading="lazy"` + явные `width`/`height`.

> **Следствие `ssr: false`:** в роутах **нельзя** использовать `action` и `headers` —
> рантайм-сервера нет. Заявки поэтому уходят в отдельную serverless-функцию (§8),
> а не в route action. Это ограничение проверено, не теоретическое.

## 7. Модели данных

> Ниже — форма данных в приложении (camelCase). Типы таблиц **генерируем** из Supabase
> в `types/database.ts`, руками их не пишем. `lib/queries.ts` маппит snake_case из БД
> в эти типы — один слой маппинга, чтобы компоненты не знали про схему БД.

```ts
type Product = {
  id: number;
  slug: string;
  name: string;
  brand: string;
  model: string;
  type: 'split' | 'multi-split' | 'mobile' | 'semi-industrial';
  priceFrom: number;               // BYN, «под ключ»: оборудование + наценка + монтаж
  images: string[];                // локальные пути
  inStock: boolean;

  // --- поля, которые ведём вручную; скрипт импорта их не трогает ---
  description: string;             // 2-3 предложения своими словами: кому и почему
  tier: 'budget' | 'optimum' | 'premium';
  featured: boolean;               // показывать в блоке «Популярные модели»
  solutionSlugs: string[];         // в каких готовых решениях участвует

  specs: {
    areaM2?: number;
    coolingKw?: number;
    heatingKw?: number;
    isInverter?: boolean;
    hasWifi?: boolean;
    refrigerant?: string;
    noiseDb?: number;
    eer?: number;
    cop?: number;
    minHeatTemp?: number;
    [key: string]: unknown;        // остальное — в таблицу «Все характеристики»
  };

};

type Solution = {
  slug: string;                    // bedroom-20, living-room-35, studio-50, office-70
  title: string;                   // «Кондиционер для спальни до 20 м²»
  areaFrom: number;
  areaTo: number;
  priceFrom: number;               // считается: дешёвая подходящая модель + монтаж

};

type Lead = {
  name: string;
  phone: string;
  message?: string;
  source: 'hero' | 'quiz' | 'product' | 'footer' | 'modal';

  quizAnswers?: Record<string, string>;
```

#### 1. Переделать фильтрацию каталога — закрыто 2026-09-08

*Сделано иначе, чем записано ниже:* не ползунки вместо фишек, а боковая панель

Сейчас в `CatalogView` фишки: пять ступеней площади, три ступени цены (считаются
от максимума и округляются до 500) и селект сортировки. Заменить на ползунки.

Что решить до кода:

- **Один ползунок или два конца.** «До 35 м²» — один; «от 15 до 35» — диапазон.
  Нативный `<input type="range">` даёт только одно значение: диапазон собирают
  из двух наложенных инпутов либо своим компонентом. Свой компонент —
  это заново стрелки, Home/End, объявление значения скринридером; нативный
  отдаёт это даром. Начинать с одного конца.
- **Запись в URL.** Состояние фильтров живёт в `useSearchParams` (осознанно:
  ссылку на выдачу можно переслать). Ползунок при перетаскивании шлёт события
  непрерывно — писать в URL на каждый пиксель нельзя. Фиксировать значение
  на отпускании (`onPointerUp` / `change`), а не на `input`.
- **Сброс хвоста.** `filterKey` в `CatalogView` сбрасывает счётчик показанных
  на 12 при смене фильтра. С непрерывным значением он сработает на каждом шаге
  перетаскивания — привязать к зафиксированному значению, не к промежуточному.
- **Грабли: товары без площади.** Сейчас фильтр `(p.specs.areaM2 ?? 0) <= limit`,
  то есть модели с пустой площадью проходят через любой фильтр. У ползунка
  с минимумом больше нуля они начнут пропадать. Решить явно: показывать всегда
  или прятать — молча менять поведение нельзя.
- Границы ползунков брать из данных (min/max по выборке), а не хардкодить:
  на страницах категорий диапазон цен другой.

### Черновая выкладка для показа заказчику

`npm run build:preview` собирает копию для показа. Отличается от боевой
тремя вещами, и все три — про то, чтобы черновик не уехал в поиск:
`Disallow: /` в robots.txt, `noindex, nofollow` в мета-тегах каждой
страницы и canonical с og-ссылками на адрес выкладки вместо заглушки.

Включается одной переменной `VITE_PREVIEW_URL` в `.env.preview` (файл
не в репозитории — `.gitignore` закрывает все `.env.*`). Пустая переменная
значит обычную сборку, так что перепутать режимы нельзя: боевая сборка
не читает этот файл вовсе.

Обе сборки дописывают `404.html` — копию SPA-оболочки. Без неё посетитель
по битой ссылке видел бы служебную заглушку хостинга, где нет ни одной
ссылки обратно на сайт.

Выкладка — это папка `build/client`, 6 МБ, 74 страницы, ничего серверного.
Ложится на любой статический хостинг **в корень домена**: пути к ассетам
абсолютные (`/assets/...`), поэтому подпапка вроде
`user.github.io/repo/` без правки `base` и `basename` не заработает.

### ⚠ Наличие техники — спросить у заказчика (поставлено 2026-09-07)

**Вопрос:** держит ли мастер что-то на складе или возит всё под заказ?

Сейчас сайт отвечает на это сам, и отвечает неправдой. Поле `inStock`
приезжает из API поставщика (`is_in_stock`) — это **склад поставщика**,
а показываем мы его так, будто это наличие у мастера. 44 модели из 50
помечены «в наличии».

Что на этом висит:

| Где | Что показывает |
|---|---|
| `ProductCard` | Бейдж «Под заказ» — то есть остальные молча читаются как «есть сейчас» |
| `product.tsx` | «В наличии» / «Под заказ, 1–2 недели». Срок тоже взят с потолка |
| `product.tsx`, JSON-LD | `availability: schema.org/InStock` — **это уже не про вёрстку**: ложный признак наличия в микроразметке нарушает правила Google для товарных данных |
| `SupplierNote` | «Больше 4000 моделей, нужной нет — привезу под заказ». Если под заказ вообще всё, строка обещает разницу, которой нет |

**Варианты ответа и что делать с каждым:**

- *Склада нет, всё под заказ* — убрать `inStock` из показа целиком, поставить
  честный срок поставки, в JSON-LD оставить только `PreOrder`. Строку
  про 4000 моделей переписать: она не про «привезу под заказ», а про то,
  что витрина — выборка, и любую модель поставщика можно заказать.
- *Что-то есть на складе* — нужен способ это вести. Из API поставщика такое
  не приходит, значит поле должно редактироваться руками — то есть ждёт
  админку (этап 6), а до неё показывать наличие нельзя.

**До ответа:** ничего не переписываем, но помним, что это не косметика —
`InStock` в микроразметке относится к товарным данным, а не к оформлению.

### Открыто — сейчас заглушки, поправим позже

| № | Что нужно | Где стоит заглушка | Насколько блокирует |
|---|---|---|---|
| 1 | **Цена монтажа** (одна цифра или таблица по мощности) | `config/pricing.ts`, `INSTALL_PRICE` | Единственная реально недостающая цифра. Без неё не показать «под ключ» — пока пишем «+ монтаж от N р.» |
| 2 | Название, слоган, логотип в векторе | `config/site.ts` + текстовый лого «КЛИМАТ ЛАЙН» | Не блокирует, меняется в одном месте |
| 3 | Реквизиты: ИП или самозанятый, УНП, адрес | `config/site.ts`, подвал и `/privacy` | Не блокирует вёрстку, но **обязательны до публикации** |
| 4 | Телефоны, мессенджеры, часы работы, зона выезда | `config/site.ts` | Не блокирует, но без них сайт не запустить |

Их нет — и это самый дорогой пробел в контенте. Для частного мастера чужие стоковые

## 13. Что изучить по стеку

Проект написан на **framework mode** React Router — это не тот роутинг, который
объявляется через `<Routes><Route/></Routes>`. Ссылки проверены 2026-09-04.

- [ ] **[Три режима React Router](https://reactrouter.com/start/modes)** — начать отсюда.
      `<Routes>` это declarative mode, есть ещё data mode и framework mode. Станет понятно,
      что framework mode — не новый синтаксис, а другой уровень: маршруты объявлены
      данными в `app/routes.ts`, чтобы сборщик прочитал их **до запуска приложения**
      и разложил страницы по HTML-файлам. С JSX-разметкой так нельзя — её надо выполнить.
- [ ] **[Route Module](https://reactrouter.com/start/framework/route-module)** — самая
      важная. Файл роута не просто компонент, а модуль с несколькими ролями:
      компонент рисует, `loader` даёт данные, `meta` отвечает за метатеги.
      Роутер читает их по именам экспортов.
- [ ] [Routing](https://reactrouter.com/start/framework/routing) — `index()`, `route()`,
      вложенность. У нас это `app/routes.ts`.
- [ ] [Data Loading](https://reactrouter.com/start/framework/data-loading) — откуда
      берётся `loaderData` в пропсах компонента.
- [ ] [Rendering](https://reactrouter.com/start/framework/rendering) — SSR, SPA
      и пререндер. Наш `ssr: false` описан там.
- [ ] **[Pre-rendering](https://reactrouter.com/how-to/pre-rendering)** — на этом стоит
      весь сайт, отсюда взят `react-router.config.ts`.
- [ ] [Переезд с component routes](https://reactrouter.com/upgrading/component-routes) —
      путь от `<Routes>` к текущему устройству, показывает что во что превращается.

**Живые примеры в проекте**, чтобы читать доки со сверкой:

| Что смотреть | Файл |
|---|---|
| Простой роут без данных | `app/routes/about/about.tsx` |
| Лоадер и параметр URL | `app/routes/catalog/catalog-category.tsx` |
| Все экспорты сразу: `loader`, `links`, `meta`, компонент | `app/routes/home/home.tsx` |
| Корень с `Outlet` и `ErrorBoundary` | `app/root.tsx` |
| Сгенерированные типы — откуда `Route.ComponentProps` знает форму данных | `.react-router/types/` |
