# База данных и админка

Схема Supabase и порядок настройки. Сама админка живёт в сайте —
`app/routes/admin/`, адрес `/admin`.

Внутри сайта, а не отдельным приложением: иначе модель данных
дублируется — типы товара, названия категорий, подписи источников
заявок. Копии совпадают ровно до первого изменения, а расходятся молча,
потому что оба проекта собираются успешно.

Публичные страницы от этого ничего не теряют: роуты бьются на куски,
и чанк с клиентом Supabase (214 КБ) загружается только тому, кто открыл
`/admin`. Проверено — в разметке главной его нет.

## Что редактируется

| Раздел | Что можно |
|---|---|
| Главная | Заметка, сводка, графики заявок и посещений, что требует внимания, контакты, реквизиты и текст первого экрана |
| Заявки | Статус и заметка. Создание и удаление недоступны: заявки приходят с сайта |
| Цены | Цена монтажа по классам площади, флаг «публиковать», состав монтажа, срок поставки, показ разделов «Работы» и «Отзывы» |
| Товары | Описание, уровень, «хит», показывать или скрыть |
| Отзывы | Добавление, правка, публикация, удаление |
| Работы | Название, описание, фотографии в Storage, публикация |

**Цены, характеристики и наличие товаров здесь не меняются** — их
перезаписывает импорт из выгрузки поставщика. Правка, живущая до следующей
выгрузки, хуже отсутствия правки.

## Настройка с нуля

### 1. Проект Supabase

[supabase.com](https://supabase.com) → New project. Регион ближе к Беларуси —
Frankfurt. Пароль базы сохраните, он понадобится редко, но понадобится.

### 2. Схема и данные

Dashboard → SQL Editor → New query. Выполнить по очереди, целиком:

1. `database/schema.sql` — таблицы, RLS, бакеты Storage.
2. `database/seed.sql` — 50 товаров, цены монтажа, настройки.
3. `database/analytics.sql` — счётчик посещений. Нужен только вместе
   с хостингом: пока `/api/track` некуда выкладывать, писать в эти таблицы
   нечему. Без него админка работает целиком, кроме цифр по трафику —
   там честно написано, что счётчик не подключён.

`seed.sql` собирается командой `npm run seed:make` из снимков в `app/data` —
руками его не правят, правки затрёт следующая генерация.

Оба файла идемпотентные: повторный запуск ничего не ломает.

Есть ещё `database/patch-source-url.sql` — разовый. Колонка `source_url`
появилась позже первого сида, и ссылки на карточки поставщика остались
только в репозитории. Выполнить один раз после `schema.sql` (он добавит
колонку) и потом удалить: следующий `seed.sql` соберётся уже со ссылками.

### 3. Кто может входить

**Authentication → Users → Add user**: почта и пароль. Больше ничего делать
не нужно — профиль заведётся сам, триггером из `schema.sql`. Имя возьмётся
из части почты до собаки: `ivan@mail.by` станет `ivan`.

Так же добавляется и второй, и третий: каждый созданный пользователь
получает доступ.

**Закройте регистрацию.** Authentication → Sign In / Providers → Email →
выключить «Allow new users to sign up». Иначе любой желающий заведёт себе
админку сам: триггер выдаёт доступ каждому созданному пользователю, а
открытая регистрация означает, что создать пользователя может кто угодно.

Чтобы задать имя и роль сразу, в форме создания раскройте **Auto Confirm
User → User Metadata** и впишите:

```json
{ "name": "Даниил", "role": "dev" }
```

Роли две: `owner` — заказчик, `dev` — разработчик. **Прав они пока не
различают**: писать в таблицы может любой вошедший. Роль сейчас нужна
только чтобы понимать, кто есть кто; когда понадобится разграничение —
оно добавляется в политики RLS, а не в интерфейс.

Поменять имя или роль позже:

```sql
update public.profiles set name = 'Даниил', role = 'dev'
where id = (select id from auth.users where email = 'ivan@mail.by');
```

Отобрать доступ — удалить пользователя в Authentication → Users. Строка
в `profiles` уйдёт следом, каскадом.

Если профиль всё-таки не создался (например, пользователь заведён до того,
как накатили схему), админка встретит сообщением о его отсутствии. Лечится
одной командой:

```sql
insert into public.profiles (id, name, role)
select id, split_part(email, '@', 1), 'owner' from auth.users
on conflict (id) do nothing;
```

### 4. Ключи

Project Settings → API. Скопировать `Project URL` и `anon public` в `.env`:

```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ...
```

Anon-ключ попадает в клиентский бандл — так и задумано, **но только при
включённом RLS**. Схема включает его на всех таблицах; если будете добавлять
таблицу, не забудьте `enable row level security`, иначе anon-ключ откроет
её на запись всему интернету.

Ключ `service_role` сюда не кладётся никогда: он обходит RLS полностью.
Он нужен только серверным обработчикам — `/api/lead` и `/api/track`, —
и живёт в переменных хостинга под именем `SUPABASE_SERVICE_ROLE_KEY`,
**без префикса `VITE_`**. С префиксом Vite подставил бы его в бандл,
и любой посетитель получил бы полный доступ к базе вместе с заявками.

### Что нужно серверным обработчикам

| Переменная | Кому | Зачем |
|---|---|---|
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | `/api/lead` | Уведомление о заявке |
| `SUPABASE_URL` | всем трём | Куда писать |
| `SUPABASE_ANON_KEY` | `/api/publish` | Проверить сессию нажавшего кнопку |
| `SUPABASE_SERVICE_ROLE_KEY` | всем трём | Запись в `leads`, `page_views` и отметки публикации мимо RLS |
| `TRACK_SALT` | `/api/track` | Соль для отпечатка посетителя — любая длинная случайная строка |
| `SITE_URL` | `/api/lead` | Ссылка на товар в сообщении |
| `BUILD_HOOK_URL` | `/api/publish` | Секретный адрес сборки от хостинга |

Локально ничего из этого дублировать не нужно: `SUPABASE_URL` и
`SUPABASE_ANON_KEY` dev-сервер берёт из `.env` (там они с префиксом `VITE_`),
а `.dev.vars` нужен только для того, что браузеру видеть нельзя.

Без `SUPABASE_URL` и ключа заявка всё равно дойдёт в телеграм, но
в админке её не будет: запись в базу сделана необязательной намеренно —
терять заявку из-за недоступной базы нельзя. В журнале сервера в этом
случае будет строка «Заявка не сохранена».

### 5. Запуск

```
npm run dev        # http://localhost:5173/admin
```

Переменные нужны и на сборке — и по двум разным причинам. `/admin` без них
соберётся, но при открытии честно скажет, что ключей нет. А публичные
страницы без них вообще не соберутся: сборка начинается с похода в базу.

## Аналитика

Свой счётчик, а не Метрика. Чужой — это скрипт весом в сотню килобайт
на каждой странице, баннер про куки и данные, которые лежат не у нас.
Здесь на странице десяток строк, на устройство посетителя не пишется
ничего, а цифры лежат в той же базе рядом с заявками — и «сколько
заходов» можно честно поделить на «сколько заявок».

Метрике это не замена: она умеет поисковые запросы, карты кликов
и рекламные кампании. Когда дойдёт до продвижения, её ставят
дополнительно, а эти цифры остаются своей независимой проверкой.

```
страница → /api/track → service_role → page_views → представления → админка
```

Персональных данных не хранится: вместо адреса — его отпечаток,
посоленный сегодняшней датой, обратно в адрес он не превращается.
Соль меняется в полночь, поэтому проследить за человеком из вчера
в сегодня нельзя. Отсюда важное следствие: **сумма посетителей по дням —
это число посещений, а не людей**. Пришедший дважды за неделю посчитан
дважды, и в админке это так и подписано.

Заявки считаются иначе — в браузере, из тех же строк, что показывает
раздел «Заявки». Представлений для них нет намеренно: второе определение
того, что такое заявка, разошлось бы с первым при первом же изменении
статусов. Побочная выгода — графики по заявкам работают, даже если
`analytics.sql` ещё не накачен.

## Публикация

Сайт — статика, и правка в админке не видна, пока его не пересобрали.
Для этого в меню админки есть кнопка «Опубликовать»: она дёргает
`/api/publish`, тот идёт по секретному адресу сборки, хостинг пересобирает
и выкладывает. Полторы-три минуты.

**Где взять адрес сборки:**

| Хостинг | Где |
|---|---|
| Netlify | Site settings → Build & deploy → Build hooks |
| Vercel | Settings → Git → Deploy Hooks |
| Cloudflare Pages | Settings → Builds & deployments → Deploy hooks |

У всех трёх это «POST по адресу, тело не нужно». Полученный адрес кладётся
в переменную `BUILD_HOOK_URL` там же, где остальные ключи. Пока её нет,
кнопка честно говорит, что публикация не настроена.

GitHub Actions тоже умеет запускаться по запросу (`repository_dispatch`),
но там нужны ещё заголовок с токеном и тело с именем события — обработчик
под это придётся дополнить.

**Как админка понимает, что есть неопубликованное.** Сборка кладёт рядом
со статикой `build-info.json` со своим временем. Админка запрашивает его
у живого сайта и сравнивает с самой свежей `updated_at` в базе. Новее
в базе — значит, есть что публиковать.

Заявки в этом сравнении не участвуют: они приходят сами, круглые сутки,
и на сайте ничего не меняют. Иначе кнопка загоралась бы после каждого
обращения клиента и очень быстро перестала бы что-либо значить.

**Кто может публиковать.** Только вошедший в админку: обработчик проверяет
токен сессии через Supabase. Без проверки адрес `/api/publish` был бы
кнопкой «запусти сборку» для всего интернета — а это минуты сборки
и деньги за них. Анонимный ключ для этого не годится и не принимается:
он публичен и лежит в бандле (проверено — Supabase отвечает на него 403).

Чаще раза в минуту сборка не запускается: вторая встаёт в очередь за первой
без всякой пользы. Отметка времени хранится в базе, а не в памяти функции —
у serverless-функции памяти между вызовами нет.

## Как данные попадают на сайт

```
Supabase → npm run data:pull → app/data/*.json → сборка → статика
```

`scripts/fetch-data.ts` забирает товары, цены и настройки и кладёт их
снимком в `app/data/products.json` и `app/data/site-data.json`. Дальше
приложение читает обычный JSON и ничего про базу не знает. Скрипт входит
в `npm run build` — отдельно его запускают, только чтобы посмотреть
свежие данные в `npm run dev`.

**Посетитель в базу не ходит.** Он получает готовый HTML: и быстрее,
и поисковик видит каталог в разметке, а не пустой контейнер. Обратная
сторона — правка в админке появляется на сайте после пересборки, а не
сразу. Для прайса и описаний это верный размен: они меняются раз в месяц,
а страницы открывают каждый день.

Снимки коммитятся. Это и запас (сборка переживёт недоступность Supabase),
и путь назад: `npm run seed:make` собирает из них `seed.sql`, которым
база поднимается заново.

Пустой каталог скрипт считает отказом и останавливает сборку. Выкатить
сайт без единого товара хуже, чем не выкатить: страницы соберутся,
поисковик их переобойдёт и увидит пустоту.

## Устройство

```
app/
├─ lib/
│  ├─ api.ts          ApiResponse: данные или ошибка, без исключений
│  ├─ supabase.ts     клиент (создаётся лениво) и разбор ошибок
│  └─ admin-api.ts    все запросы и формы строк
├─ hooks/
│  ├─ useRows.ts      загрузка списка — один хук на все разделы
│  ├─ useSave.ts      сохранение поля с паузой, без кнопки «Сохранить»
│  └─ authContext.ts  сессия
├─ components/admin/  мелкие элементы интерфейса
└─ routes/admin/      layout с формой входа + пять разделов
```

Клиент Supabase создаётся при первом обращении, а не при загрузке модуля:
сайт пререндерится целиком, и модуль, падающий без переменных окружения,
уронил бы сборку публичных страниц из-за инструмента, к которому они
отношения не имеют.

Ошибки не бросаются исключениями: в интерфейсе почти каждая — сообщение
человеку («нет прав», «сессия истекла»), а через `throw` их приходится
ловить в каждом обработчике, и один забытый `catch` роняет страницу
вместо кнопки.

Сохранение идёт само, с паузой 600 мс после последней клавиши. Кнопка
«Сохранить» на каждую мелочь — лишний клик и лишний повод забыть нажать.
